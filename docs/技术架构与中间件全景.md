## 二、什么是"中间件"，为什么需要它

### 2.1 用生活比喻理解

假设你开一家小饭馆：

| 角色 | 对应技术 | 干什么 |
|---|---|---|
| 服务员 | 前端 | 接待客人、记录需求、把菜端上来 |
| 厨师 | 后端业务代码 | 真正做菜的人 |
| 仓库 | MySQL | 存放食材，随时取用 |
| 出菜口的临时台面 | Redis | 炒好的菜先放这，服务员马上端走，不用等 |
| 采购员 | Maven / npm | 去外面把需要的工具和材料买回来 |
| 厨房管理系统 | Spring 框架 | 规定谁干什么、怎么配合 |

**"中间件"就是那些"不属于业务本身，但没有它整个系统就跑不顺"的基础设施。**

### 2.2 中间件在项目里的三大类

| 类别 | 项目里有哪些 | 作用 |
|---|---|---|
| **数据存储类** | MySQL、Redis | 存数据 |
| **连接管理类** | Druid 连接池 | 管理数据库连接的复用，避免反复开关连接 |
| **服务框架类** | Spring Boot、MyBatis | 提供程序运行的骨架，简化开发 |

### 2.3 判断"要不要引入一个中间件"的标准

**不是为了用而用。** 每个中间件都增加了复杂度，引入它必须有明确理由：

| 中间件 | 引入理由 | 不用会怎样 |
|---|---|---|
| MySQL | 数据必须持久化 | 一关程序数据全丢 |
| Redis | 高频读写数据库扛不住 | 热门资料被反复查库，数据库压力大 |
| Druid | 每次新建数据库连接很慢 | 每个请求都花时间建连接，慢 |
| JWT | 前后端分离需要无状态认证 | 得用 Session，服务器要记状态，扩展难 |

## 四、前端技术逐个说明

### 4.1 Vue 3 —— 画页面的框架

**是什么**：一套让 HTML 页面"能跟着数据自动变化"的工具。

**为什么需要**：传统的 HTML 页面，数据变了要手动去改页面元素。
Vue 让你只改数据，页面自己更新。

**在项目里干什么**：
- `frontend/src/views/Home.vue` 定义了首页长什么样
- 后端返回 `javaVersion: "11.0.5"`，页面上自动显示出来，不用手动改 HTML

**不用会怎样**：需要手写大量 DOM 操作代码，页面一复杂就无法维护。

**关键概念**（不需要会写，知道即可）：
- `.vue` 文件 = 一个页面或一个组件
- `<template>` 里的内容 = 页面结构
- `<script setup>` 里的内容 = 页面逻辑
- `<style scoped>` 里的内容 = 这个页面专属的样式

---

### 4.2 Vite —— 开发服务器 + 打包工具

**是什么**：前端的"启动器"和"打包机"。

**两个核心作用**：

**作用一：开发时启动一个服务器**
执行 `npm run dev` 后，它启动 `http://localhost:5173`，
你改代码，浏览器立刻自动刷新 —— 这叫**热更新**。

**作用二：把一堆文件打包成能部署的成品**
执行 `npm run build` 后，它把几十个 `.vue` / `.js` 文件
合并压缩成几个小文件放到 `dist/` 目录，可以直接丢到服务器上。

**配置在**：`frontend/vite.config.js`

**还有一个重要功能：代理**
```
浏览器请求 localhost:5173/api/health
    ↓ Vite 发现以 /api 开头
转发到 localhost:8080/api/health
    ↓
后端处理并返回
```
**为什么要这样**：浏览器有"同源策略"，5173 端口的页面直接请求 8080 端口会被拦。
让 Vite 帮忙转发，浏览器就以为是同一个来源，不拦了。

---

### 4.3 Element Plus —— 现成的 UI 组件库

**是什么**：别人写好的一整套界面组件。

**为什么需要**：如果每个按钮、表格、弹窗都自己从零写样式，
一个项目要做几个月。用组件库，一行代码就能加一个漂亮的表格。

**在项目里干什么**：
- 首页的卡片、描述列表、进度条
- 登录页的输入框、表单校验
- 后续的表格、分页、上传控件

**举例**：
```html
<el-button type="primary">登录</el-button>
```
这一行就得到一个带样式的蓝色按钮，不用写任何 CSS。

---

### 4.4 Vue Router —— 页面跳转

**是什么**：管理"哪个网址显示哪个页面"。

**在项目里干什么**：
- `#/` → 首页
- `#/login` → 登录页
- 其他 → 404 页面

**配置在**：`frontend/src/router/index.js`

**两个高级但重要的功能**：

**① 路由懒加载**
```js
component: () => import('@/views/Home.vue')
```
意思是"用户真的访问这个页面了，才去下载它的代码"。
好处：首屏加载快。构建日志里能看到 Home 和 Login 各自是独立文件，就是这个原因。

**② 登录守卫**
在 `index.js` 里有个 `beforeEach`，它会在每次跳转前检查：
"这个页面需要登录吗？用户有令牌吗？"没有就跳登录页。

---

### 4.5 Pinia —— 跨页面共享数据

**是什么**：一个"全局数据仓库"。

**为什么需要**：举个例子——
用户登录后，登录信息要在「首页」「资料页」「个人中心」都能用。
如果每个页面各自去问一次后端，就重复了。
Pinia 让你登录一次存起来，所有页面都能读。

**在项目里干什么**：
- 存当前登录用户的信息
- 存课程的筛选条件（切页面回来还在）

**目前状态**：项目已装好但暂未使用，M1 阶段接入登录后启用。

---

### 4.6 Axios —— 前后端通信的桥梁

**是什么**：负责把请求发给后端、把结果拿回来的工具。

**为什么不用浏览器自带的 `fetch`**：
因为 Axios 提供了"拦截器"，能统一处理三件麻烦事。

**在项目里干什么**（配置在 `frontend/src/api/request.js`）：

| 拦截器 | 做的事 | 好处 |
|---|---|---|
| 请求拦截器 | 自动在每个请求上加上登录令牌 | 业务代码不用每次手动加 |
| 响应拦截器 | 自动把 `{code, message, data}` 拆开，只留 `data` | 业务代码更简洁 |
| 错误处理 | 后端报错自动弹出提示 | 不用每个页面写一遍错误提示 |

**举个实际效果**：
```js
// 业务代码里只写这一行
const data = await getHealth()
// 拿到的 data 直接就是 { status: "UP", javaVersion: "11.0.5" }
// 不用写 data.data.code === 0 之类的判断
```

## 五、后端技术逐个说明

### 5.1 Spring Boot —— 后端的骨架

**是什么**：一套让 Java Web 程序"能跑起来"的基础框架。

**为什么需要它**：不用 Spring Boot 的话，你需要自己配置：
服务器怎么启动、请求怎么路由、数据库怎么连、JSON 怎么转……
配置代码比业务代码还多。

Spring Boot 把这些都做好了，你只需要写业务。

**在项目里干什么**：
- `CourseHubApplication.java` 是启动入口，运行它的 `main` 方法整个后端就起来了
- 内嵌了 Tomcat 服务器，不需要单独装一个 Tomcat
- 自动读取 `application.yml` 里的配置

**关键注解**（看到就知道什么意思就行）：
| 注解 | 作用 |
|---|---|
| `@SpringBootApplication` | 标记这是启动类 |
| `@RestController` | 标记这个类提供 HTTP 接口 |
| `@Service` | 标记这是业务层组件 |
| `@Mapper` | 标记这是数据库访问组件 |

---

### 5.2 Spring MVC —— 请求分发

**是什么**：Spring Boot 里负责"把请求交给正确的函数处理"的部分。

**工作方式**：
```
浏览器请求 GET /api/health
    ↓
Spring MVC 查路由表：这个地址该谁处理？
    ↓
找到 HealthController.health() 方法
    ↓
调用它
```

**在项目里干什么**：
`HealthController.java` 上写了 `@RequestMapping("/api/health")`，
所以访问这个地址就会执行里面的 `health()` 方法。

---

### 5.3 MyBatis —— Java 与数据库之间的翻译官

**是什么**：负责执行 SQL、把数据库的一行行数据变成 Java 对象的工具。

**为什么选它而不是 JPA**：
- JPA 会自动生成 SQL，你**看不到**实际执行了什么
- MyBatis 让你**手写 SQL**，性能问题一眼能看出来

对课程项目来说，能展示 SQL 功底是加分项。

**在项目里的分工**：
| 位置 | 放什么 |
|---|---|
| `mapper/` 目录 | Java 接口，声明"我要查什么" |
| `resources/mapper/` 目录 | XML 文件，写真正的 SQL |

**配置在**：`application.yml` 的 `mybatis` 部分
其中 `map-underscore-to-camel-case: true` 很关键 ——
它让数据库的 `create_time` 自动对应 Java 的 `createTime`，不用手动转换。

---

### 5.4 Druid —— 数据库连接池

**这是最容易被忽略但很重要的一个。**

**先理解问题**：
每次访问数据库，都要经历：
`建立网络连接 → 验证身份 → 执行 SQL → 关闭连接`
其中"建立连接"最慢，可能占 80% 的时间。

如果每个请求都重新建连接，网站会非常慢。

**Druid 怎么解决**：
启动时先建好 5 个连接，放在池子里。
请求来了，从池子里借一个用，用完还回去。
**不用反复"开户"，直接"借用"。**

**额外好处：自带监控页面**
访问 `http://localhost:8080/druid/`（账号 admin / 密码 admin）
能看到：执行了多少条 SQL、哪条最慢、有多少并发。
**答辩时可以拿这个页面做演示。**

**配置在**：`application-dev.yml` 的 `druid` 部分
```yaml
initial-size: 5     # 启动时先建 5 个连接
min-idle: 5         # 最少保持 5 个空闲连接
max-active: 20      # 最多 20 个连接（超了要排队）
```

---

### 5.5 Spring AOP —— 无侵入地加功能

**是什么**：一种"在不修改原始代码的前提下，给方法加额外动作"的技术。

**为什么需要**：
假设你要给所有"增删改"操作记录日志。
不用 AOP：要在 20 个方法里各写一遍日志代码。
用 AOP：写一个切面，自动套在所有方法上。

**在项目里计划干什么**（`aspect/` 目录，待 M3 实现）：
- **操作日志**：谁在什么时候删了什么资料，自动记录
- **幂等校验**：防止用户狂点提交按钮产生重复数据
- **接口限流**：限制某个接口的访问频率

---

### 5.6 JWT —— 登录凭证

**是什么**：一段加密字符串，证明"你是谁"。

**为什么需要**：
前后端分离后，后端不保存"谁在线"这个状态。
用户登录成功后，后端发一个 JWT 字符串给前端。
前端每次请求都带上它，后端一看就知道是谁。

**工作流程**：
```
① 用户输入 admin / admin123，点登录
② 后端校验密码（用 BCrypt 比对）
③ 校验通过 → 生成 JWT（里面写着用户 id 和角色）→ 返回给前端
④ 前端存到 localStorage
⑤ 之后每个请求的请求头都带：Authorization: Bearer <这串 JWT>
⑥ 后端拦截器解析它，确认身份，放行
```

**为什么安全**：
JWT 是用密钥签名的。别人就算改了里面的内容，签名也会对不上，后端会拒绝。

**已配置在**：`application.yml` 的 `coursehub.jwt` 部分
**待实现**：拦截器和登录接口（M1 阶段）

---

### 5.7 BCrypt —— 密码加密

**是什么**：一种专门用于存密码的加密算法。

**为什么不用 MD5**：
MD5 太快了，黑客用普通显卡一秒能试几十亿次。
BCrypt 故意设计得很慢，每次加密结果还不一样（自带随机盐），
即使两个人密码相同，存进去的哈希也完全不同。

**在项目里**：
- 数据库里 `sys_user.password` 字段存的是 BCrypt 哈希
- 种子数据里的哈希是真实生成并验证过的（`admin` / `admin123`）

**注意**：哈希是**单向**的，不能反推出原密码。
登录时是"把用户输入再加密一次，跟数据库里的比对"。

---

### 5.8 Lombok —— 少写重复代码

**是什么**：一个帮你自动生成代码的小工具。

**作用**：一个 Java 类通常要写几十个 getter/setter 方法。
Lombok 让你只写一个注解：
```java
@Data
public class User {
    private Long id;
    private String username;
}
```
编译时它自动补上 `getId()`、`setUsername()` 等方法。

**在项目里**：所有实体类、DTO、VO 都用了 `@Data`；日志用了 `@Slf4j`。

---

### 5.9 Knife4j —— 自动生成接口文档

**是什么**：根据代码里的注解，自动生成一个网页版的接口文档。

**在项目里干什么**：
访问 `http://localhost:8080/doc.html`，能看到：
- 所有接口列表
- 每个接口要传什么参数
- **可以直接在网页上点"发送"测试接口**

**为什么有价值**：前后端联调时，前端同学不用问后端"这个接口怎么传参"，
打开文档自己看就行。

## 六、数据存储逐个说明

### 6.1 MySQL —— 主数据库（"仓库"）

**存什么**：所有需要**永久保存**的数据。

**在项目里存的 16 张表**（详见第十节）：
用户、学院、课程、章节、资料、文件、版本、评论、收藏、下载记录、举报、标签、通知、日志

**为什么用 MySQL 而不是文件**：
- 能按条件快速查询（找"计算机学院 2026 年秋季的所有课程"）
- 能保证数据一致（转账时两边同时成功或同时失败）
- 能全文检索（搜"数据结构"能找到"数据结构与算法"）

**项目特有的用法**：
用了 MySQL 的 **FULLTEXT ngram 全文索引**实现中文搜索。
普通网盘只能按文件名搜，我们能搜标题、描述、标签，这是差异点。

**连接信息**（配置在 `application-dev.yml`）：
- 地址：`localhost:3306`
- 数据库名：`coursehub`
- 用户名：`root`
- 密码：**不写在代码里**，放在 `application-local.yml`（已被 gitignore，不会上传）

### 6.2 Redis —— 缓存（"临时记录板"）

**是什么**：一个把所有数据放在**内存**里的数据库。

**为什么快**：内存读写比硬盘快几百倍。

**在项目里干什么**（4 个用途）：

| 用途 | 具体做什么 | 不用会怎样 |
|---|---|---|
| **登录令牌** | 存 JWT，支持"强制下线" | 无法主动让某人退出登录 |
| **下载计数** | 用 `INCR` 累加，定时批量写回 MySQL | 热门资料被高频更新，数据库行锁竞争 |
| **排行榜** | 用有序集合存贡献榜 | 每次都要 `ORDER BY` 全表排序，慢 |
| **上传进度** | 记录已上传的分片编号 | 断点续传无法实现 |

**为什么这些场景不能用 MySQL**：
这些操作**频率极高、精度要求低、丢了影响不大**。
下载次数从 100 变成 101 晚几秒同步，没人会在意；
但如果每次都去改数据库，热门资料那一行会被反复加锁，拖垮整个表。

**连接信息**：`localhost:6379`，本机无密码

**运维提示**：Redis 需要手动启动（双击 `E:\java\redis\start.bat`），
它是"服务器程序"，启动后窗口会一直停着，这是正常的。

## 八、一次请求的完整旅程

**以首页加载为例，追踪整个流程。这是理解全栈项目最关键的一环。**

```
【第 1 步】你在浏览器打开 http://localhost:5173
    → Vite 开发服务器返回 index.html + Vue 代码
    → Vue 开始渲染页面
        · 解析 Home.vue
        · 画出顶部导航、卡片骨架
        · 执行 onMounted(checkHealth)  ← 页面加载完成时自动触发

【第 2 步】checkHealth() 调用 getHealth()
    → Axios 发起请求：GET /api/health
    → 请求拦截器先执行：如果有登录令牌，加到请求头
    → 因为地址以 /api 开头，请求发到 5173（Vite）

【第 3 步】Vite 的代理规则匹配到 /api
    → 把请求转发到 http://localhost:8080/api/health
    → 这一步解决了跨域问题

【第 4 步】请求到达后端 Tomcat（内嵌在 Spring Boot 里）
    → Spring MVC 查路由表：/api/health 该谁处理？
    → 找到 HealthController 的 health() 方法

【第 5 步】进入 Controller 层
    → health() 方法组装要返回的数据
    → 注意：这里没查数据库，因为只是健康检查
    → 真正的业务接口会往下走到 Service 层，这里演示完整路径：
        Controller → Service → Mapper

【第 6 步】（如果是查数据的接口）Service 层
    → 权限校验：这个人有权看这个数据吗？
    → 业务逻辑：比如算可信度评分
    → 开启事务：多个数据库操作要么全成功要么全失败

【第 7 步】Mapper 层执行 SQL
    → 从 Druid 连接池借一个连接
    → 执行 SQL：SELECT ... FROM resource WHERE ...
    → MySQL 返回结果集
    → MyBatis 把结果集转换成 Java 对象
    → 连接还给池子

【第 8 步】（如果有缓存）先问 Redis
    → 如果 Redis 里有，直接返回，根本不查 MySQL
    → 这叫"缓存命中"，能省下大量时间

【第 9 步】Controller 把结果包装成统一格式
    → Result.ok(data)
    → 得到 {"code":0,"message":"ok","data":{...},"timestamp":...}

【第 10 步】Spring MVC 把 Java 对象自动转成 JSON 字符串
    → 通过 HTTP 响应发回去

【第 11 步】回到前端
    → Axios 响应拦截器收到 {"code":0,...,"data":{...}}
    → 检查 code：是 0 就成功，把 data 部分交给业务代码
    → 不是 0 就弹错误提示

【第 12 步】Vue 拿到数据
    → healthData.value = {...}
    → Vue 检测到数据变了，自动更新页面
    → 状态卡从"正在检测"变成绿色"后端连接正常"
    → 页面上显示出 Java 版本、服务器时间等
```

**如果中间任何一步出错会怎样**：

| 出错位置 | 结果 |
|---|---|
| 后端没启动 | 代理转发失败，前端显示"后端未连接" |
| 数据库连不上 | 启动时就报错，应用起不来 |
| SQL 有语法错误 | 该接口返回 500，全局异常处理器记录日志 |
| 用户没登录 | 拦截器返回 401，前端跳登录页 |
| 权限不足 | Service 层抛 BizException，返回 403 |
| Redis 挂了 | 缓存功能降级，但主流程仍可用（设计上不让它阻塞） |

## 九、项目的分层架构

### 9.1 后端三层职责

```
┌─────────────────────────────────────────────────────────┐
│  Controller 接口层    （controller/ 目录）                │
│  ─────────────────────────────────────────────────────  │
│  ✅ 收 HTTP 请求、解析参数、@Valid 校验                   │
│  ✅ 调用 Service，把结果包装成 Result 返回                 │
│  ❌ 不写业务逻辑                                          │
│  ❌ 不直接操作数据库                                      │
│                                                          │
│  类比：餐厅服务员。只负责点单和上菜，不炒菜。               │
└───────────────────────────┬─────────────────────────────┘
                            ▼
┌─────────────────────────────────────────────────────────┐
│  Service 业务层       （service/ 和 service/impl/）       │
│  ─────────────────────────────────────────────────────  │
│  ✅ 业务规则判断（"资料超过 500MB 不允许上传"）             │
│  ✅ 事务控制（@Transactional，保证数据一致）               │
│  ✅ 权限校验（"这个人能删这条资料吗"）                      │
│  ✅ 编排多个 Mapper（一次业务可能要查好几张表）             │
│  ❌ 不拼 SQL                                              │
│                                                          │
│  类比：厨师长。掌握菜谱（业务规则），指挥下面的人。           │
└───────────────────────────┬─────────────────────────────┘
                            ▼
┌─────────────────────────────────────────────────────────┐
│  Mapper 数据访问层    （mapper/ + resources/mapper/）     │
│  ─────────────────────────────────────────────────────  │
│  ✅ 执行 SQL、把结果映射成 Java 对象                       │
│  ❌ 不写业务判断                                          │
│                                                          │
│  类比：仓库管理员。只听指令取货，不管你要货干什么用。          │
└───────────────────────────┬─────────────────────────────┘
                            ▼
                    【 MySQL 数据库 】
```

### 9.2 为什么必须分层

**如果不分层**，所有代码都写在 Controller 里：

| 问题 | 后果 |
|---|---|
| 想换个接口地址 | 得把业务逻辑一起翻出来改 |
| 想给多个接口加日志 | 每个接口都要改一遍 |
| 想写单元测试 | 依赖 HTTP 环境，很难测 |
| 两个人同时改 | 都改同一个文件，冲突不断 |

**分层之后**：
- 改接口地址 → 只动 Controller
- 改业务规则 → 只动 Service
- 改 SQL → 只动 Mapper
- 加日志 → 用 AOP 统一加

### 9.3 Entity / DTO / VO 为什么要分三个

这三个都长得差不多，初学者最容易困惑。

| 类型 | 全称 | 用途 | 举例 |
|---|---|---|---|
| **Entity** | 实体 | 对应**数据库表**的结构 | `User` 有 `password` 字段 |
| **DTO** | Data Transfer Object | 接收**前端传来**的参数 | `LoginDTO` 只有 `username` + `password` |
| **VO** | View Object | 返回**给前端**的数据 | `UserVO` 没有 `password` 字段 |

**为什么不能混用**：
如果直接把 `Entity` 返回给前端，`password` 字段就泄露了。
所以必须要转一道，只挑能给的字段放进 `VO`。

**这也是答辩时"你考虑过安全吗"的标准答案之一。**

### 10.2 三个必须理解的设计

#### ① 为什么 `file` 和 `resource` 要分开

**问题**：两位老师可能传同一份课程大纲，如果每个资料都存一份文件，就浪费空间。

**解决**：文件独立存储，资料通过 `file_id` 引用它。
`file.ref_count` 记录被引用了几次，归零才能删物理文件。

**好处**：
- 同一份文件只存一次
- 秒传：上传前先算 MD5，发现已存在就直接建关联，**零传输**
- 删除安全：还有资料引用它时不允许删文件

#### ② 为什么 `resource_version` 是树形而不是链形

**链形版本**（普通网盘的做法）：v1 → v2 → v3
问题：两个人同时改同一份资料，后提交的会覆盖前一个。

**树形版本**（我们的做法）：
```
v1
 ├── v2 ── v3   （A 同学：补充第五章）
 └── v2' ── v3' （B 同学：重写第二章）
```
`parent_version_id` 字段指向父版本，构成一棵树。
支持分支、合并、回滚，而且每步都留痕。

#### ③ 索引是干什么的

**索引就像书的目录。** 没有目录，找某个内容要一页页翻（全表扫描）。

项目里几个关键索引：

| 索引 | 服务什么场景 |
|---|---|
| `idx_course_status_score` | 查"某课程下已发布的资料，按可信度排序" —— 列表页最常用 |
| `ft_resource`（全文索引） | 中文搜索 |
| `uk_username`（唯一索引） | 保证用户名不重复，同时让登录查询变快 |

**"最左前缀原则"**（答辩高频问点）：
组合索引 `(course_id, status, score)` 只能从最左边开始用。
能服务 `WHERE course_id=?`，能服务 `WHERE course_id=? AND status=?`，
但**不能**服务单独的 `WHERE status=?`。所以字段顺序很重要。

## 十二、术语速查表

| 术语 | 通俗解释 |
|---|---|
| **前后端分离** | 前端和后端是两个独立程序，通过 HTTP 接口通信 |
| **RESTful** | 一种接口设计风格，用 `GET` 查、`POST` 增、`PUT` 改、`DELETE` 删 |
| **JSON** | 一种数据格式，`{"name":"张三","age":20}` |
| **跨域** | 浏览器安全策略，不同端口/域名之间默认不能互相请求 |
| **代理** | 帮你去请求别的地址，绕过跨域限制 |
| **路由** | "什么网址显示什么页面"的规则 |
| **懒加载** | 用到时才加载，而不是一次性全加载 |
| **依赖** | 别人写好的库，你的项目用到了它 |
| **依赖注入** | 对象不由自己 new，由框架创建好"给"你 |
| **注解** | 以 `@` 开头的标记，告诉框架这个类/方法要特殊处理 |
| **ORM** | 对象关系映射，让 Java 对象和数据库表自动对应 |
| **连接池** | 预先建好一批数据库连接重复使用 |
| **事务** | 一组操作要么全成功要么全失败 |
| **缓存** | 把常用数据放在快速存储里，避免重复计算/查询 |
| **缓存命中** | 需要的数据正好在缓存里，不用查数据库 |
| **缓存穿透** | 查一个不存在的数据，缓存和数据库都没有，每次都查库 |
| **幂等** | 同一个操作执行多次，结果和执行一次一样 |
| **乐观锁** | 更新前先检查数据有没有被别人改过 |
| **N+1 查询** | 查 10 条主记录，又为每条单独查一次关联，共 11 次查询（性能问题） |
| **全表扫描** | 没有索引，逐行查找，数据量大时极慢 |
| **索引最左前缀** | 组合索引必须从最左边的字段开始用才生效 |
| **Token** | 令牌，证明身份的凭证 |
| **JWT** | 一种 Token 格式，内容自包含、带签名 |
| **BCrypt** | 专门用来加密密码的算法，故意设计得很慢 |
| **哈希** | 单向加密，只能加密不能解密 |
| **盐（Salt）** | 加密时掺入的随机值，让相同密码产生不同结果 |
| **统一响应体** | 所有接口返回同样的外层结构，方便前端统一处理 |
| **全局异常处理** | 所有异常在一个地方统一处理，业务代码不用到处 try-catch |
| **DTO / VO** | 入参对象 / 出参对象 |
| **环境隔离** | dev/prod 配置分开，防止开发配置误用到生产 |

## 附：快速定位问题该看哪

| 现象 | 先看哪里 |
|---|---|
| 页面白屏 | 浏览器 F12 → Console 有报错 |
| 接口 404 | 检查 Controller 的 `@RequestMapping` 路径 |
| 接口 401 | Token 过期或没带 Token |
| 接口 403 | 有身份但没权限，检查数据权限校验 |
| 接口 500 | 看后端控制台的异常堆栈 |
| 数据没保存 | 看日志里 SQL 有没有执行，事务有没有回滚 |
| 列表很慢 | `EXPLAIN` 看有没有走索引 |
| 前端改了没反应 | 确认 `npm run dev` 还在跑 |
| 后端改了没生效 | 需要重启后端（Java 不是热更新的） |
