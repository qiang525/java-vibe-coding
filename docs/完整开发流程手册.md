# 第 0 章 先搞懂：这个项目由哪些部分组成

## 0.1 一句话说明

CourseHub 是一个**课程资料协作平台** —— 学生可以按课程上传、查找、下载课件，
并且每份资料都有"可信度评分"，让你知道哪份靠谱。

## 0.2 技术组成（每一块负责什么）

```
┌─────────────────────────────────────────────────────────────┐
│  浏览器                                                      │
│      ↓ 访问 http://localhost:5173                            │
├─────────────────────────────────────────────────────────────┤
│  前端：Vue 3 + Element Plus + Vite + Pinia + Axios           │
│    · Vue 3         页面框架（把数据渲染成界面）               │
│    · Element Plus  组件库（按钮、表格、弹窗，不用自己写样式）  │
│    · Vite          构建工具（开发时热更新、打包时压缩）        │
│    · Pinia         状态管理（全局共享登录状态）               │
│    · Axios         发 HTTP 请求（自动带 Token、统一处理错误）  │
│      ↓ 请求 /api/**（Vite 代理转发到 8080）                   │
├─────────────────────────────────────────────────────────────┤
│  后端：Spring Boot 2.7 + MyBatis + Druid + Redis + JWT        │
│    · Spring Boot   应用框架（内嵌 Tomcat，一个 jar 就能跑）    │
│    · Spring MVC    处理 HTTP 请求（Controller 层）            │
│    · MyBatis       操作数据库（手写 SQL，可控性强）            │
│    · Druid         数据库连接池（复用连接，自带监控）          │
│    · Redis         缓存（存搜索热词、上传进度）               │
│    · JWT           登录凭证（无状态，服务端不存 session）      │
│      ↓ SQL                                                    │
├─────────────────────────────────────────────────────────────┤
│  存储：MySQL 8.0（业务数据）+ 本地磁盘（上传的文件）           │
└─────────────────────────────────────────────────────────────┘
```

## 0.4 一次请求的完整旅程（**看懂这个就看懂了整个项目**）

以"用户刷新资料列表"为例：

```
① 浏览器：Vue 组件 mounted 时调用 getResources()
② Axios 请求拦截器：从 localStorage 取 Token，加到请求头
③ 请求发到 http://localhost:5173/api/resources
④ Vite 开发服务器：发现是 /api 开头 → 转发给 localhost:8080
⑤ Spring 拦截器 AuthInterceptor：
      - 解析 Token → 存进 ThreadLocal（UserContext）
      - 检查方法上有没有 @RequireLogin
⑥ Spring MVC 路由：把请求交给 ResourceController.list()
⑦ Controller：调用 resourceService.pageResources(query)
⑧ Service：注入当前用户身份，调用 resourceMapper.selectPage()
⑨ MyBatis：把 XML 里的 SQL 拼好，通过 Druid 连接池发给 MySQL
⑩ MySQL：执行 SQL，返回结果集
⑪ MyBatis：把结果集映射成 Java 对象（下划线自动转驼峰）
⑫ Service：处理业务（补 canEdit 字段等），包装成 PageResult
⑬ Controller：包装成统一响应体 Result
⑭ Jackson：把 Java 对象序列化成 JSON
⑮ 拦截器 afterCompletion：清理 ThreadLocal（重要！）
⑯ 浏览器：Axios 响应拦截器解包 {code, message, data}，返回 data
⑰ Vue：把数据渲染到页面上
```

**每一层都在做自己该做的事**，这就是"分层架构"的意义。

# 第 1 章 环境准备：每个软件是干什么的

## 1.1 为什么需要这些软件

| 软件 | 为什么需要 | 不用会怎样 |
|---|---|---|
| **JDK 11** | Java 代码要被 JVM 执行 | 程序跑不起来 |
| **Maven** | 管理 Java 依赖、编译打包 | 得手动下载几百个 jar 包 |
| **MySQL 8** | 存业务数据（用户、课程、资料） | 数据重启就丢 |
| **Redis** | 存临时数据（热词、上传进度） | 功能能用，但性能差、断点续传没了 |
| **Node.js** | 运行前端构建工具 | 前端代码没法编译 |
| **Git** | 版本控制 | 改错了回不去 |

## 1.2 本项目用到的版本

| 软件 | 版本 | 本项目路径 |
|---|---|---|
| JDK | 11 | `E:\java\jdk11` |
| Maven | 3.9.16 | `E:\java\apache-maven-3.9.16` |
| MySQL | 8.2 | `E:\java\MySQL` |
| Redis | 8.10.2 | `E:\java\redis` |
| Node.js | 24 | `E:\node.js` |

> ⚠️ **为什么一定要 JDK 11**：项目用的是 Spring Boot 2.7，它兼容 JDK 8/11/17，
> 但 Spring Boot 3.x 才要求 JDK 17。用 11 是稳妥选择。
> 同时 **MySQL 必须 8.0+**，因为中文全文检索依赖 `ngram` 分词器（5.7 没有）。

## 1.3 环境变量 JAVA_HOME 怎么配

**它是什么**：告诉系统和工具"JDK 装在哪"。

**怎么配**（Windows）：

```
右键「此电脑」→ 属性 → 高级系统设置 → 环境变量
→ 系统变量 → 新建
   变量名：JAVA_HOME
   变量值：E:\java\jdk11
→ 确定，然后重启命令行窗口
```

**怎么验证**：

```cmd
echo %JAVA_HOME%
java -version
```

应该输出 `11.0.5` 或类似的 11.x 版本。

**常见错误**：命令行里 `java` 命令报错，但 `mvn` 正常 ——
说明 PATH 里有失效的 java 路径，而 Maven 走的是 JAVA_HOME。
（本项目就踩过这个坑，见第 17 章）

# 第 2 章 从零建工程：项目骨架怎么搭

## 2.1 顺序很重要

建工程要**从外往里**建：

```
① 建根目录 + Git 初始化
② 建后端工程（Maven 结构）
③ 建前端工程（Vite 结构）
④ 建数据库
⑤ 把三方串起来（配置代理、跨域、数据库连接）
```

## 2.2 第 1 步：根目录与 Git

```bash
mkdir D:\桌面\Java项目AIGC
cd D:\桌面\Java项目AIGC
git init
```

**要马上去建 `.gitignore`**，否则后面编译产物、依赖包、密码文件都会被提交。

`.gitignore` 至少要排除：

```gitignore
# 编译产物
target/
dist/
node_modules/

# 敏感配置（含密码）
backend/src/main/resources/application-local.yml

# 上传的文件
backend/upload/

# 日志
*.log
```

> ⚠️ **`.gitignore` 必须在第一次提交前就建好**。
> 如果先提交了 `target/` 再加 `.gitignore`，那些文件已经在版本库里了，
> 需要 `git rm -r --cached target` 才能移除。

## 2.3 第 2 步：后端工程结构

手工建这些目录（Maven 有标准结构，不能随便改）：

```
backend/
├── pom.xml                                    ← 依赖清单
└── src/main/
    ├── java/com/nnuist/coursehub/             ← 源码
    └── resources/                              ← 资源文件
        ├── application.yml
        └── mapper/                             ← MyBatis 的 SQL
```

**`pom.xml` 是什么**：相当于"零件清单"，声明要用哪些第三方库。

关键依赖及作用：

| 依赖 | 作用 |
|---|---|
| `spring-boot-starter-web` | Spring MVC + 内嵌 Tomcat |
| `mybatis-spring-boot-starter` | MyBatis 与 Spring 的整合 |
| `mysql-connector-java` | Java 连 MySQL 的驱动 |
| `druid-spring-boot-starter` | 数据库连接池 |
| `spring-boot-starter-data-redis` | 操作 Redis |
| `spring-boot-starter-validation` | 参数校验（`@NotBlank` 等） |
| `spring-boot-starter-aop` | 切面（操作日志用） |
| `jjwt` | 生成和解析 JWT |
| `spring-security-crypto` | 只为了用 BCrypt（不引入整个 Security） |
| `knife4j-spring-boot-starter` | 接口文档（`doc.html`） |
| `lombok` | 自动生成 getter/setter，少写几百行 |

> 💡 **为什么不用 Spring Security 全家桶**：
> 我们只需要 BCrypt 加密和简单的鉴权，用自定义拦截器更透明、更好理解。
> 引入整个 Security 反而会让流程变复杂。

## 2.4 第 3 步：前端工程结构

```bash
# 在 frontend 目录
npm init -y
npm install vue vue-router pinia element-plus axios
npm install -D vite @vitejs/plugin-vue
```

**`vite.config.js` 里最关键的一段是代理配置**：

```js
server: {
  proxy: {
    '/api': {
      target: 'http://localhost:8080',
      changeOrigin: true
    }
  }
}
```

**为什么需要它**：前端跑在 5173，后端跑在 8080。
浏览器认为这是"跨域"（端口不同），会直接拦截请求。

配了代理后，前端代码里写 `/api/health` 就行，
**Vite 会帮你转发到 8080**，浏览器以为是同源，不拦截了。

## 2.5 第 4 步：把两边连起来

**后端要允许跨域**（万一没走代理时也能用）：

```java
@Configuration
public class CorsConfig implements WebMvcConfigurer {
    @Override
    public void addCorsMappings(CorsRegistry registry) {
        registry.addMapping("/**")
                .allowedOriginPatterns("*")
                .allowedMethods("GET", "POST", "PUT", "DELETE", "OPTIONS")
                .allowCredentials(true)
                .maxAge(3600);
    }
}
```

**验证连通性**：在首页放一个"健康检查"卡片，
调 `GET /api/health`，能返回 `{code:0}` 就说明链路通了。

> 💡 **这是个好习惯**：搭完骨架先做"能跑通"的验证，
> 而不是直接写业务功能。否则出了问题不知道是架构问题还是业务问题。

**你可以自己验证**：
```bash
curl http://localhost:8080/api/health
# 或者在浏览器直接打开这个地址
```

# 第 3 章 数据库设计：16 张表是怎么定下来的

## 3.1 设计顺序（不是想到哪建到哪）

```
① 先画"实体"——  系统里有哪些"东西"？（用户、课程、资料、文件…）
② 再定"关系"——  它们之间是什么关系？（一对多？多对多？）
③ 再补"属性"——  每个实体需要存什么字段？
④ 最后加"索引"—— 哪些查询最频繁？给它建索引。
```

## 3.2 本项目 16 张表的分组

| 分组 | 表 | 解决什么问题 |
|---|---|---|
| **用户与权限** | `sys_user`、`sys_college` | 谁在用 |
| **课程体系** | `course`、`course_member`、`chapter` | 资料放在哪 |
| **文件与资料** | `file`、`resource`、`resource_version` | 资料本身是什么 |
| **互动与治理** | `comment`、`collection`、`download_record`、`report`、`tag`、`resource_tag`、`notification`、`audit_log` | 怎么互动、怎么管 |

## 3.3 多对多关系怎么处理（重点）

**问题**：一个用户能加多门课，一门课有多个用户。存一张表里？做不到。

**解法**：建**中间表** `course_member`：

```sql
CREATE TABLE course_member (
    id        BIGINT UNSIGNED AUTO_INCREMENT,
    course_id BIGINT UNSIGNED NOT NULL,
    user_id   BIGINT UNSIGNED NOT NULL,
    role      VARCHAR(20) DEFAULT 'STUDENT',
    joined_at DATETIME DEFAULT CURRENT_TIMESTAMP,
    PRIMARY KEY (id),
    UNIQUE KEY uk_course_user (course_id, user_id)   -- ← 关键
);
```

**`uk_course_user` 唯一索引的两个作用**：
1. 查得快（"这个人在不在这门课里"）
2. **防重复加入** —— 用户连点两次"加入"，第二次会被数据库拒绝

## 3.4 索引怎么定（三个真实例子）

### 例子 1：`resource` 表的列表页查询

**查询长这样**：

```sql
SELECT ... FROM resource
WHERE course_id = ? AND status = 'PUBLISHED'
ORDER BY score DESC LIMIT 10;
```

**建索引**：

```sql
KEY idx_course_status_score (course_id, status, score DESC)
```

**为什么这么建**：筛选条件 `course_id`、`status` 在前，
排序字段 `score` 在后 —— **筛选和排序一次搞定**。

**验证方式**：

```sql
EXPLAIN SELECT ...;
-- 看 Extra 列，如果出现 Using filesort 说明排序没走索引
```

### 例子 2：中文搜索用全文索引

```sql
FULLTEXT KEY ft_resource (title, description) WITH PARSER ngram
```

**为什么不用普通索引**：`LIKE '%关键词%'` 开头是通配符，索引无法定位起点。
必须用全文索引 + ngram 分词器（专门处理中文）。

### 例子 3：**最左前缀原则**

组合索引 `(a, b, c)`：

| 查询条件 | 能用索引吗 |
|---|---|
| `WHERE a = ?` | ✅ 能 |
| `WHERE a = ? AND b = ?` | ✅ 能 |
| `WHERE a = ? AND b = ? AND c = ?` | ✅ 能 |
| `WHERE b = ?` | ❌ **不能**（跳过了最左的 a） |
| `WHERE a = ? AND c = ?` | ⚠️ 只能用 a 那一部分 |

**原因**：索引像电话簿，先按姓排、再按名排。
你不知道姓，就没法用这个排序去找。

## 3.5 冗余字段的取舍

`course` 表里有两个"算出来"的字段：

```sql
member_count   INT,   -- 成员数
resource_count INT,   -- 资料数
```

**理论上可以每次 `COUNT(*)` 现算**，但那样：

```
课程列表 20 条 → 每条 COUNT 一次关联查询 → 21 次数据库往返
```

这叫 **N+1 查询问题**，数据一多就拖垮数据库。

**所以**：存一份冗余计数，在变更时维护。

```java
// 发布资料时
courseMapper.increaseResourceCount(courseId, +1);

// 删除资料时
courseMapper.increaseResourceCount(courseId, -1);
```

**代价**：数据存了两份，可能不一致。这是"**用写入成本换读取性能**"的权衡。

# 第 4 章 后端基础：统一响应、异常、分页

## 4.1 为什么第一件事是写这三个

因为它们**所有接口都要用**。如果先写业务，后面再补，就得改几十个文件。

## 4.2 统一响应体 `Result`

**长这样**：

```json
{
  "code": 0,
  "message": "ok",
  "data": { },
  "timestamp": 1759300000000
}
```

**为什么必须统一**：如果每个接口返回结构不同，前端要写 N 套解析代码。

前端只需要一个判断：

```js
if (res.code === 0) {
  return res.data      // 成功，把数据交给页面
} else {
  ElMessage.error(res.message)   // 失败，统一弹提示
}
```

## 4.3 错误码分段

| 段位 | 含义 | 例子 |
|---|---|---|
| `0` | 成功 | — |
| `400xx` | 参数错误 | `40001` 参数校验失败 |
| `401xx` | 认证问题 | `40101` 未登录、`40104` 账号密码错误 |
| `403xx` | 权限不足 | `40301` 无权操作 |
| `404xx` | 资源不存在 | `40403` 课程不存在 |
| `409xx` | 状态冲突 | `40906` 已加入课程 |
| `410xx` | 文件相关 | `41002` 文件太大 |
| `500xx` | 服务端错误 | `50000` 系统繁忙 |

**好处**：看到一个码就知道该找谁 —— `4xxxx` 是调用方问题，`5xxxx` 是服务端问题。

## 4.4 全局异常处理

**解决的问题**：不写 try-catch 也能统一处理错误。

```java
@RestControllerAdvice
public class GlobalExceptionHandler {

    @ExceptionHandler(BizException.class)
    public Result<Void> handleBiz(BizException e) {
        return Result.fail(e.getCode(), e.getMessage());
    }

    @ExceptionHandler(MethodArgumentNotValidException.class)
    public Result<Void> handleValid(MethodArgumentNotValidException e) {
        // 把 Bean Validation 的报错信息抽出来给前端
        String msg = e.getBindingResult().getFieldErrors().stream()
                .map(FieldError::getDefaultMessage)
                .collect(Collectors.joining("; "));
        return Result.fail(ResultCode.PARAM_ERROR, msg);
    }

    @ExceptionHandler(Exception.class)
    public Result<Void> handleOther(Exception e) {
        log.error("未预期的异常", e);
        return Result.fail(ResultCode.SYSTEM_ERROR);
    }
}
```

**关键点**：
- 业务异常（能预料到的）→ 返回具体错误码，**不打印堆栈**
- 系统异常（bug）→ 打印完整堆栈到日志，但**只给前端返回"系统繁忙"**（不泄露内部信息）

## 4.5 分页组件

**统一分页参数** `PageQuery`：

```java
public class PageQuery {
    private Integer page = 1;
    private Integer pageSize = 10;

    public Integer getPageSize() {
        // 关键：防止前端传 pageSize=999999 把数据库拖垮
        return Math.min(pageSize, 100);
    }

    public Integer getOffset() {
        return (getPage() - 1) * getPageSize();
    }
}
```

**统一分页结果** `PageResult`：

```json
{
  "list": [...],
  "total": 128,
  "page": 1,
  "pageSize": 10,
  "pages": 13
}
```

**为什么要有 `MAX_PAGE_SIZE`**：不限制的话，一个人传 `pageSize=999999`，
数据库要一次吐出全部数据，内存和网络都会爆。

# 第 5 章 M1 认证：JWT + 拦截器 + 注解鉴权

## 5.1 为什么用 JWT 而不是 Session

| 方案 | 原理 | 问题 |
|---|---|---|
| **Session** | 服务端存一份登录记录，给浏览器一个 sessionId | 多台服务器时，A 服务器存的 session，B 服务器不认 |
| **JWT** | 把用户信息加密签名后交给浏览器保管 | 无法主动失效（要配合黑名单） |

**本项目选 JWT**：无状态，天然支持多机部署。

## 5.2 JWT 长什么样

```
eyJhbGciOiJIUzI1NiJ9 . eyJ1c2VySWQiOjEsInJvbGUiOiJBRE1JTiJ9 . 签名
      ↑Header              ↑Payload（Base64，谁都能解开看）    ↑签名
```

> ⚠️ **重要**：Payload 是 **Base64 编码，不是加密**！谁都能解开看。
> 所以**绝对不能往 JWT 里放密码**。

**安全性靠什么**：签名是用只有服务端知道的密钥算出来的。
改了 Payload，签名就对不上，服务端会拒绝。

## 5.3 密码为什么用 BCrypt

```java
private final BCryptPasswordEncoder encoder = new BCryptPasswordEncoder();

// 注册：加密后存
user.setPassword(encoder.encode(rawPassword));

// 登录：把用户输入重新加密后比对（不是解密！）
if (!encoder.matches(rawPassword, user.getPassword())) {
    throw new BizException(ResultCode.LOGIN_FAILED);
}
```

**BCrypt 的三个特点**：

| 特点 | 说明 |
|---|---|
| **单向** | 加密后无法还原，只能"比对" |
| **自带盐** | 同一个密码每次加密结果都不同（防彩虹表） |
| **故意慢** | 一次加密约 100ms，暴力破解代价极高 |

**对比 MD5**：MD5 快到一秒能算几十亿次，用来存密码等于没加密。

## 5.4 拦截器怎么工作

```java
public class AuthInterceptor implements HandlerInterceptor {

    @Override
    public boolean preHandle(HttpServletRequest request, ...) {
        // ① 解析 Token（不管接口要不要登录，先试着解析）
        String token = extractToken(request);
        if (token != null) {
            Claims claims = jwtUtil.parseToken(token);
            if (claims != null) {
                // 存进 ThreadLocal，后面的代码就能直接读到"当前用户是谁"
                UserContext.set(new CurrentUser(userId, username, role));
            }
        }

        // ② 检查接口是否需要登录
        if (needLogin(handlerMethod) && !UserContext.isLoggedIn()) {
            throw new BizException(ResultCode.UNAUTHORIZED);
        }

        // ③ 检查角色要求
        RequireRole requireRole = getAnnotation(handlerMethod, RequireRole.class);
        if (requireRole != null && !allowed) {
            throw new BizException(ResultCode.NO_PERMISSION);
        }
        return true;
    }

    @Override
    public void afterCompletion(...) {
        UserContext.clear();      // ⚠️ 这一行绝对不能省！
    }
}
```

## 5.5 【重点】ThreadLocal 为什么必须清理

**Tomcat 的线程是复用的**。假设不清理：

```
请求 A（用户张三）→ 线程 1 → 存入 张三 信息 → 处理完，不清理
请求 B（用户李四）→ 复用 线程 1 → 读到残留的 张三 信息 → 越权！
```

**这就是真实的越权漏洞**。所以 `afterCompletion` 里必须 `UserContext.clear()`。

## 5.6 注解式权限

```java
@Target({ElementType.METHOD, ElementType.TYPE})
@Retention(RetentionPolicy.RUNTIME)
public @interface RequireLogin { }
```

**用起来**：

```java
@RequireLogin
@GetMapping("/me")
public Result<UserVO> currentUser() {
    return Result.ok(userService.getUserVOById(UserContext.getUserId()));
}
```

**好处**：想给某个接口加权限，加一行注解就行，
不用在每个方法里重复写判断代码。

## 5.7 【重点】防用户枚举

```java
// 账号不存在
if (user == null) {
    throw new BizException(ResultCode.LOGIN_FAILED);   // 40104
}
// 密码错误
if (!encoder.matches(...)) {
    throw new BizException(ResultCode.LOGIN_FAILED);   // 同样的 40104
}
```

**为什么返回同一个错误**：如果分开返回，攻击者可以批量试账号，
靠"提示不同"判断出哪些账号真实存在，然后针对性爆破。

# 第 6 章 M1 课程：一个完整的 CRUD 长什么样

## 6.1 每层要写什么（以"创建课程"为例）

```
Controller 层  →  接收参数、校验、调 Service、包装响应  （3 行代码）
Service 层     →  业务规则、权限校验、事务控制           （主要逻辑在这）
Mapper 层      →  执行 SQL                              （不写业务判断）
```

**Controller 长这样**（注意有多短）：

```java
@ApiOperation("创建课程")
@RequireLogin
@PostMapping
public Result<Long> create(@Valid @RequestBody CourseSaveDTO dto) {
    return Result.ok("课程创建成功", courseService.createCourse(dto));
}
```

> 💡 **Controller 只有两三行是正常的**。如果里面有几十行逻辑，说明分层被破坏了。

## 6.2 DTO / Entity / VO 为什么要分三个

| 类 | 作用 | 关键点 |
|---|---|---|
| `CourseSaveDTO` | **接收**前端参数 | 只开放该让前端填的字段 |
| `Course`（Entity） | **对应**数据库表 | 有 ownerId、memberCount 等 |
| `CourseVO` | **返回**给前端 | 含 JOIN 出来的 collegeName |

**具体例子**：

```java
// DTO 里没有 ownerId —— 因为让前端传的话，用户能把自己伪造成负责人
// Service 层强制从 Token 里取：
course.setOwnerId(UserContext.getUserId());
```

## 6.3 数据权限：Service 层必须做的事

```java
private void checkOwnerPermission(Course course) {
    Long uid = UserContext.getUserId();
    if (!course.getOwnerId().equals(uid) && !UserContext.isAdmin()) {
        throw new BizException(ResultCode.FORBIDDEN);
    }
}
```

**为什么拦不住**：`@RequireLogin` 只能判断"登录了没"，
判断不了"这门课是不是你的"。

**如果不写这段**：任何登录用户改一下 URL 里的课程 ID，就能改别人的课程 ——
这是**水平越权漏洞**。

## 6.4 MyBatis 动态 SQL

**需求**：课程列表要支持"按关键词、按学院、按学期"筛选，但每个条件都是可选的。

**传统写法**（痛苦）：

```java
String sql = "SELECT * FROM course WHERE 1=1";
if (keyword != null) sql += " AND name LIKE ...";
if (collegeId != null) sql += " AND college_id = ...";
```

**MyBatis 写法**：

```xml
<select id="selectPage" resultType="CourseVO">
    SELECT ... FROM course c
    <where>
        c.is_deleted = 0
        <if test="q.keyword != null and q.keyword != ''">
            AND (c.name LIKE CONCAT('%', #{q.keyword}, '%') OR ...)
        </if>
        <if test="q.collegeId != null">
            AND c.college_id = #{q.collegeId}
        </if>
    </where>
</select>
```

**`<where>` 标签的妙处**：它会自动去掉第一个多余的 `AND`，
所以不用写 `WHERE 1=1` 那种凑数写法。

## 6.5 `#{}` 和 `${}` 的区别（安全要点）

| 写法 | 效果 | 安全性 |
|---|---|---|
| `#{name}` | 编译成 `?` 占位符 | ✅ **安全**，自动防注入 |
| `${name}` | 直接字符串拼接 | ❌ **危险**，SQL 注入 |

**永远用 `#{}`**。只有动态表名、动态排序字段这种"不能当参数传"的场景
才用 `${}`，且必须做白名单校验。

## 6.6 事务控制

```java
@Override
@Transactional(rollbackFor = Exception.class)
public Long createCourse(CourseSaveDTO dto) {
    courseMapper.insert(course);                      // ① 插课程
    courseMapper.insertMember(course.getId(), uid, "OWNER");   // ② 加入成员表
    return course.getId();
}
```

**为什么加 `@Transactional`**：这两步必须**要么都成功、要么都不做**。
如果 ① 成功 ② 失败，就会出现"课程建好了但创建者不是成员"的脏数据。

**`rollbackFor = Exception.class` 的作用**：
默认只对 `RuntimeException` 回滚，加上它连受检异常也回滚。

# 第 7 章 M2 文件上传：五重安全校验

## 7.1 为什么"上传文件"是最危险的功能之一

因为它是**唯一让用户能把任意内容送进服务器的入口**。
一个没做好校验的上传接口，可能导致：
- 上传木马并在服务器上执行
- 覆盖系统文件（路径穿越）
- 把磁盘撑爆
- 泄露服务器目录结构

## 7.2 五重校验，每重防什么

| # | 校验 | 防什么问题 |
|---|---|---|
| ① | 判空 | 前端漏传、请求截断 |
| ② | 判大小（500MB） | 有人传 10GB 文件占满磁盘 |
| ③ | **扩展名白名单** | 上传 `.exe` / `.jsp` 等可执行文件 |
| ④ | **文件头（魔术数字）** | **改扩展名的伪装文件** |
| ⑤ | **UUID 重命名 + 路径穿越防护** | `../../windows/system32` 攻击 |

## 7.3 为什么扩展名用白名单

```
黑名单思路：禁止 .exe .bat .sh .jsp ...
→ 攻击者找个你没列的后缀（.py、.pl、新出现的）就绕过了

白名单思路：只允许 .pdf .docx .jpg ...
→ 不在名单里的一律拒绝（默认拒绝）
```

**这就是"allowlist 优于 denylist"原则。**

## 7.4 文件头校验（最容易被忽略的一步）

**问题**：扩展名只是文件名的后缀，改起来太容易。

```bash
mv trojan.exe 课件.pdf     # 扩展名检查完全拦不住
```

**解法**：看文件内容的头几个字节（**格式本身决定的，改不了**）：

| 格式 | 文件头 |
|---|---|
| PDF | `25 50 44 46`（`%PDF`） |
| PNG | `89 50 4E 47` |
| JPG | `FF D8 FF` |
| ZIP/docx/xlsx/pptx | `50 4B 03 04`（`PK..`） |
| RAR | `52 61 72 21`（`Rar!`） |

```java
if (FileUtil.needsMagicCheck(ext) && !FileUtil.matchesMagicNumber(tempFile, ext)) {
    throw new BizException(ResultCode.FILE_TYPE_NOT_ALLOWED, "文件内容与扩展名不符，已拒绝");
}
```

> ⚠️ **注意**：`txt` / `md` 是纯文本，没有固定文件头，要**跳过**这个校验。
> 任何安全措施都要考虑"误杀正常文件"的代价。

## 7.5 路径穿越攻击（最隐蔽的一个）

**如果拿用户的文件名直接拼路径**：

```java
Path target = rootPath.resolve(userFileName);   // rootPath = D:/upload
```

用户传文件名 `../../../../Windows/System32/drivers/etc/hosts`，
拼出来化简后就跑到系统目录了 —— **能读、甚至能覆盖系统文件**。

**防御代码**：

```java
private Path resolveSafely(String relativePath) {
    Path target = rootPath.resolve(relativePath).normalize();   // ①拼接 ②化简
    if (!target.startsWith(rootPath)) {                         // ③必须在根目录内
        throw new BizException(ResultCode.FORBIDDEN, "非法的文件路径");
    }
    return target;
}
```

> ⚠️ **顺序不能反**：必须先 `normalize()` 再 `startsWith()`。
> 反过来 `a/../../b` 这种写法就能绕过。

**本项目还有第二道防线**：分片上传的 `fileHash` 用正则限制成 32 位十六进制：

```java
if (fileHash == null || !fileHash.matches("^[a-fA-F0-9]{32}$")) {
    throw new BizException(ResultCode.PARAM_ERROR, "文件哈希格式不正确");
}
```

这样它**不可能**包含 `/` 或 `..`，路径穿越彻底不可能。

## 7.6 秒传与引用计数

**秒传原理**：

```
上传前先算文件 MD5 → 拿这个值去 file 表查
    命中 → 只把 ref_count +1，不写磁盘（毫秒完成）
    未命中 → 正常走完整流程
```

**引用计数为什么必要**：

同一份文件可能被多份资料引用。如果删除资料时直接删物理文件，
**其他还在用它的资料就打不开了**。

所以：

```java
fileMapper.decreaseRefCount(id);
FileInfo after = fileMapper.selectById(id);
if (after.getRefCount() <= 0) {
    fileStorage.delete(path);       // 真的没人用了，才删
    fileMapper.deleteById(id);
}
```

# 第 8 章 M2 资料管理：三级可见性

## 8.1 三种可见性

| 级别 | 谁能看 | 场景 |
|---|---|---|
| `PUBLIC` | 所有人（含未登录） | 公开讲义、真题 |
| `COURSE_ONLY` | 本课程成员 + 课程负责人 | 课程内部资料 |
| `PRIVATE` | 仅上传者 | 个人笔记 |

另外：**上传者本人和管理员**对所有级别都有访问权。

## 8.2 权限过滤写在 SQL 里，不是查出来再过滤

```xml
<if test="q.isAdmin == null or q.isAdmin == false">
    AND (
        r.visibility = 'PUBLIC'
        <if test="q.currentUserId != null">
            OR r.uploader_id = #{q.currentUserId}
            OR (r.visibility = 'COURSE_ONLY' AND EXISTS (
                    SELECT 1 FROM course_member cm
                    WHERE cm.course_id = r.course_id AND cm.user_id = #{q.currentUserId}
                ))
            OR EXISTS (SELECT 1 FROM course c2
                       WHERE c2.id = r.course_id AND c2.owner_id = #{q.currentUserId})
        </if>
    )
</if>
```

**两个好处**：
1. **高效** —— 数据库直接少返回数据，不用查 10000 条扔掉 9990 条
2. **安全** —— 就算业务代码漏写判断，SQL 这层还兜着

## 8.3 `currentUserId` 必须由服务端注入

```java
public PageResult<ResourceVO> pageResources(ResourceQueryDTO query) {
    // 前端就算传了 currentUserId 也会被这行覆盖
    query.setCurrentUserId(UserContext.getUserId());
    query.setIsAdmin(UserContext.isAdmin());
    ...
}
```

否则用户传个 `currentUserId=999` 就能看别人的资料。

## 8.4 发布资料为什么"两步走"

```
① POST /api/files/upload   → 拿到 fileId
② POST /api/resources      → 传 fileId + 课程/标题，正式发布
```

**好处**：
- 大文件可以先花几分钟传完，传完再填标题
- 秒传时第二步只需毫秒
- 文件模块和资料模块职责清晰

## 8.5 发布资料时的三步写入

```java
resourceMapper.insert(resource);        // ① 插资料主记录
versionMapper.insert(version);          // ② 插入 v1 版本（指向文件）
resourceMapper.update(pointer);         // ③ 回填 current_version_id
```

**为什么分三步**：`version` 的 ID 要等插入后才知道，
所以只能先插 resource、再插 version、最后回填指针。
**这三步在同一事务里**，不会出现中间状态。

## 8.6 版本表的存在意义

`resource` 表里没有 `file_id`，而是 `current_version_id` 指向版本表。

**为什么**：资料会被修改。如果直接存 `file_id`，每次修改只能覆盖，**历史全丢**。

有了版本表：
- 历史完整保留
- 支持回滚（把指针指回旧版本）
- 支持分支（多人从同一版本各自改）

# 第 9 章 M2 分片上传：Redis 首次登场

## 9.1 为什么需要分片上传

| 问题 | 后果 |
|---|---|
| 断了要从头来 | 500MB 传到 99% 断网，前功尽弃 |
| 服务端压力大 | 要一次性接收整个文件 |

**解法**：切成 5MB 一块分别传，任何一块失败只重传那一块。

## 9.2 三个接口的配合

```
① GET  /api/files/chunk/check    → 能秒传吗？之前传到哪了？
② POST /api/files/chunk/upload   → 循环上传每个分片
③ POST /api/files/chunk/merge    → 合并 + 全文件 MD5 复验
```

## 9.3 Redis 存什么

```
key:   coursehub:upload:chunk:{文件MD5}
type:  Set
value: {"0", "1", "2"}   ← 已上传的分片序号
TTL:   24 小时
```

**为什么用 Set 不用 List**：Set **天然去重**。
用户重传了第 3 片，`SADD` 不会重复计数。用 List 就会变成 `[0,1,2,2,3]`，算错。

**为什么放 Redis 不放 MySQL**：
- 上传进度是**临时状态**，传完就没用了
- 写入**极频繁**（500MB 文件要写 100 次）
- 需要**自动过期**（用户传一半走了）

## 9.4 一个容易忽略的细节

**校验分片是否齐全时，看磁盘而不是看 Redis**：

```java
for (int i = 0; i < totalChunks; i++) {
    if (!Files.exists(dir.resolve(String.valueOf(i)))) {
        missing.add(i);
    }
}
```

**为什么**：Redis 可能已过期（24 小时后清空），但磁盘上的分片还在。
**磁盘才是事实来源**，Redis 只负责快速查询进度。

## 9.5 合并后的 MD5 复验（最不该省的一步）

```
前端算的 MD5   = 基于「原始文件」
服务端算的 MD5 = 基于「合并后的文件」
             ↓ 必须完全一致
```

**不一致说明**：分片损坏 / 乱序 / 截断。

**不做会怎样**：用户会拿到一个"看着正常但打不开"的坏文件，
而且可能很久之后才发现。

**代价**：合并时多算一次 MD5（500MB 约 1 秒），换来"绝不会存坏文件"。

# 第 10 章 M2 全文检索：为什么不用 LIKE

## 10.1 `LIKE '%关键词%'` 的根本问题

```sql
SELECT * FROM resource WHERE title LIKE '%数据结构%';
```

**索引用不上**。因为索引是"按开头排序"的，
你告诉数据库"开头我不管，中间包含就行"，它只能**全表扫描**。

**EXPLAIN 实证**：

```
type: ALL        ← 全表扫描
key:  NULL       ← 没用索引
```

## 10.2 全文索引的正解

```sql
-- 建表时
FULLTEXT KEY ft_resource (title, description) WITH PARSER ngram
```

```sql
-- 查询时
SELECT id, title,
       MATCH(title, description) AGAINST('数据结构' IN BOOLEAN MODE) AS relevance
FROM resource
WHERE MATCH(title, description) AGAINST('数据结构' IN BOOLEAN MODE)
ORDER BY relevance DESC;
```

**EXPLAIN 实证**：

```
type: fulltext      ← 走全文索引
key:  ft_resource
```

## 10.3 `ngram` 是什么

MySQL 自带的全文索引按**空格**分词，对中文没用（中文没有空格）。
`ngram` 分词器会把中文按 N 个字切：

```
"数据结构" → ["数据", "据结", "结构"]     （ngram_token_size=2，默认）
```

所以它能命中"数据结构与算法"这种词。

## 10.4 为什么要返回 `relevance`

```sql
MATCH(...) AGAINST(...) AS relevance
ORDER BY relevance DESC, score DESC, created_at DESC
```

**先按相关度**（匹配得好的排前面），**再按可信度**，**最后按时间**。

相关性排序的权重不好自己算，交给 MySQL 最省事。

## 10.5 搜索热词用 ZSet

```
ZINCRBY coursehub:search:hot 1 "数据结构"     ← 每搜一次加 1 分
ZREVRANGE coursehub:search:hot 0 9 WITHSCORES ← 取前 10 名
```

**为什么用 ZSet**：它天然支持"按分数排序取前 N 名"，正好是热词榜的需求。

## 11.1 Axios 封装（前端最重要的一段代码）

```js
// 请求拦截器：自动带 Token
request.interceptors.request.use((config) => {
  const token = getToken()
  if (token) {
    config.headers['Authorization'] = `Bearer ${token}`
  }
  // FormData 请求要删掉默认的 Content-Type，否则后端解析不出文件
  if (config.data instanceof FormData) {
    delete config.headers['Content-Type']
  }
  return config
})

// 响应拦截器：统一解包 + 统一错误处理
request.interceptors.response.use(
  (response) => {
    const res = response.data
    if (res == null || typeof res.code === 'undefined') return res   // 文件流等原样返回
    if (res.code === 0) return res.data                              // 成功，直接给 data

    // 401xx 认证问题：清 Token 并跳登录
    if (res.code >= 40101 && res.code <= 40199) {
      removeToken()
      location.hash = '#/login'
    }
    ElMessage.error(res.message)
    return Promise.reject(new Error(res.message))
  },
  (error) => { /* HTTP 层错误处理 */ }
)
```

## 11.4 前端算大文件 MD5

**问题**：50MB 文件直接读进内存算 MD5 会把浏览器卡死。

**解法**：分片读取 + 增量计算。

```js
const chunks = Math.ceil(file.size / CHUNK_SIZE)
const spark = new SparkMD5.ArrayBuffer()
const reader = new FileReader()
let current = 0

reader.onload = (e) => {
  spark.append(e.target.result)      // 增量追加，不用一次读完
  current++
  if (current < chunks) {
    loadNext()
  } else {
    resolve(spark.end())
  }
}
```

**效果**：无论文件多大，内存里始终只有 5MB。

# 第 12 章 M3 协作：版本树、评论、收藏、举报

## 12.1 版本树：回滚要"留痕"

**普通做法**（不好）：把 `current_version_id` 指回旧版本，删掉中间版本。

**问题**：历史断链，看不出"什么时候改的、什么时候回滚的"。

**本项目做法**：**回滚也是生成一个新版本**。

```java
ResourceVersion version = new ResourceVersion();
version.setFileId(target.getFileId());        // 内容取自目标版本
version.setIsRollback(1);                     // 标记是回滚产生的
version.setRollbackFromVersionId(versionId);  // 记录从哪回滚来的
versionMapper.insert(version);
moveCurrentVersion(resource, version.getId());
```

**效果**：

```
v1 → v2 → v3(回滚到v1，内容同v1)     ← 三步都看得见
```

**为什么复用了 `target.getFileId()` 而不是复制文件**：
文件内容一样，没必要占两份空间。引用同一个文件即可。

## 12.2 两级评论怎么查最高效

**错误做法**（N+1）：

```java
for (CommentVO top : topList) {
    top.setReplies(commentMapper.selectByRootId(top.getId()));   // 循环里查
}
// 10 条一级评论 = 10 次查询
```

**正确做法**（2 次查询）：

```java
// ① 查一级评论
List<CommentVO> topList = commentMapper.selectTopLevel(resourceId, offset, size);

// ② 一次把所有回复查回来（WHERE root_id IN (...)）
List<Long> rootIds = topList.stream().map(CommentVO::getId).collect(toList());
List<CommentVO> allReplies = commentMapper.selectRepliesByRootIds(rootIds);

// ③ 内存里按 rootId 分组，贴回一级评论
Map<Long, List<CommentVO>> replyMap = allReplies.stream()
        .collect(groupingBy(CommentVO::getRootId));
topList.forEach(vo -> vo.setReplies(replyMap.getOrDefault(vo.getId(), emptyList())));
```

## 12.3 多态关联：一张表管三种举报

```sql
`target_type` VARCHAR(20),   -- RESOURCE / COMMENT / USER
`target_id`   BIGINT
```

**好处**：不用建三张举报表。

**代价**：查询时要按类型取不同表的名字：

```sql
CASE rp.target_type
    WHEN 'RESOURCE' THEN (SELECT title FROM resource WHERE id = rp.target_id)
    WHEN 'COMMENT'  THEN (SELECT LEFT(content, 50) FROM comment WHERE id = rp.target_id)
    WHEN 'USER'     THEN (SELECT nickname FROM sys_user WHERE id = rp.target_id)
END AS target_title
```

**这是"灵活性 vs 查询性能"的典型权衡。**

## 12.4 防重复操作用两道防线

```java
// 第一道：先查一次，给友好提示
if (collectionMapper.countByUserAndResource(uid, resourceId) > 0) {
    throw new BizException(ResultCode.ALREADY_COLLECTED);
}
collectionMapper.insert(uid, resourceId, folder);

// 第二道：数据库唯一索引兜底
// UNIQUE KEY uk_user_resource (user_id, resource_id)
```

**为什么两道都要**：并发场景下，两个请求同时查都查不到，然后都去插入 ——
第一道拦不住。**唯一索引是最后保险**。

# 第 13 章 M4 治理：评分模型与操作审计

## 13.1 可信度评分模型

**要解决的问题**：按时间排，最新上传的可能是垃圾；按下载量排，老资料永远霸榜。

**解法**：五因子加权。

```
score = 0.25 × 资料完整度     （描述、章节、标题、文件）
      + 0.20 × 上传者信用分
      + 0.20 × 社区评价        （0-5 分映射到 0-100）
      + 0.25 × 社区认可度      （下载/收藏/评论）
      + 0.10 × 时效性          （每学期衰减 15%）
```

## 13.2 认可度为什么要取对数

**如果不取对数**：一个 10000 次下载的资料，认可度是 100；
新资料 0 次下载，认可度 0。差距 100 倍，新资料**永远起不来**。

**取 `log10` 之后**：

| 下载量 | log10 归一化后 |
|---|---|
| 10 | 约 33 |
| 100 | 约 67 |
| 1000 | 约 100 |
| 10000 | 约 133 → 截断到 100 |

差距从 100 倍缩小到 3 倍，**给了新资料冒头的机会**。

## 13.3 时效性衰减

```java
long months = ChronoUnit.MONTHS.between(createdAt, now);
double terms = months / 6.0;                        // 6 个月 = 1 学期
double factor = Math.pow(1 - 0.15, terms);          // 每学期 ×0.85
return factor * 100;
```

| 上传时间 | 时效性得分 |
|---|---|
| 刚上传 | 100 |
| 1 学期后 | 85 |
| 2 学期后 | 72 |
| 3 学期后 | 61 |

**为什么用指数而不是线性**：指数衰减前期慢、后期快，更符合"知识老化"的实际情况。

## 13.4 为什么定时算而不是实时算

**实时算的问题**：列表 10 条资料 → 10 次计算 + 查上传者信用分，
每次用户刷新都算一遍，性能不可接受。

**定时算的好处**：评分本来就是"允许延迟几分钟"的数据，
批量算好存进字段，列表页直接读。

**这是典型的"离线计算 + 在线读取"模式。**

## 13.5 AOP 切面记录操作日志

**不用 AOP 的痛点**：每个要记日志的接口都要写一段 `auditLogMapper.insert(...)`，
代码重复且容易漏。

**AOP 的用法**：

```java
@LogOperation(value = "重算可信度评分", targetType = "SYSTEM")
@PostMapping("/recalc-score")
public Result<Integer> recalcScore() { ... }
```

```java
@Around("@annotation(logOperation)")
public Object around(ProceedingJoinPoint pjp, LogOperation anno) throws Throwable {
    Object result = pjp.proceed();     // 先执行目标方法

    try {
        record(pjp, anno);             // 成功后才记录
    } catch (Exception e) {
        log.warn("记录操作日志失败", e);   // ⚠️ 记日志失败不能影响业务
    }
    return result;
}
```

**两个设计要点**：
1. 用 `@Around` 而不是 `@AfterReturning` —— 要拿到注解对象和参数
2. **记日志失败绝不能抛异常** —— 否则用户操作成功但界面报错

## 13.6 审计日志为什么要存 `username` 快照

因为审计的核心是**永久可追溯**。
如果只存 `user_id`，用户被删除后就查不出"这是谁干的"。

    """发请求，返回 (状态码, 响应体)"""

    req.add_header('Content-Type', 'application/json;charset=UTF-8')

        req.add_header('Authorization', 'Bearer ' + token)

        with opener.open(req, timeout=30) as r:
            return r.status, json.loads(r.read().decode('utf-8'))

        return e.code, json.loads(e.read().decode('utf-8'))

# 第 16 章 部署上线

> 详细步骤见 `docs/部署上线指南.md`，这里讲**原理**。

## 16.1 架构变化

```
开发时：  浏览器 → 前端(5173) → 后端(8080) → MySQL + Redis
               ↑ 两个端口，浏览器认为跨域

上线后：  浏览器 → Nginx(80)
                    ├── 静态文件（HTML/CSS/JS）
                    └── /api/** → 后端(8080) → MySQL + Redis
               ↑ 只有一个入口，天然同源
```

## 16.2 为什么必须有 Nginx

| 作用 | 说明 |
|---|---|
| **反向代理** | 后端的 8080 不用对外暴露 |
| **静态文件** | Nginx 返回静态文件比 Java 快几个数量级 |
| **gzip** | 传输体积减少 60-70% |
| **统一入口** | 解决跨域、方便加 HTTPS |

## 16.3 Nginx 配置里三个不能忘的点

```nginx
# ① 不设这个，上传大文件报 413
client_max_body_size 600M;

# ② SPA 应用必须配，否则刷新 /resources/1 会 404
location / {
    try_files $uri $uri/ /index.html;
}

# ③ 大文件上传要放宽超时
location /api/ {
    proxy_read_timeout 300s;
    proxy_request_buffering off;
}
```

## 16.4 Docker 多阶段构建

```dockerfile
# 阶段一：构建（需要完整的 Maven + JDK，几百 MB）
FROM maven:3.9-eclipse-temurin-11 AS builder
COPY backend/pom.xml .
RUN mvn dependency:go-offline -B        # 先下依赖，利用 Docker 缓存
COPY backend/src ./src
RUN mvn clean package -DskipTests

# 阶段二：运行（只需要 JRE，几十 MB）
FROM eclipse-temurin:11-jre
COPY --from=builder /build/target/*.jar app.jar
ENTRYPOINT ["java", "-jar", "app.jar"]
```

**好处**：最终镜像只有几十 MB，而不是几百 MB。

**为什么先 COPY pom.xml 再 COPY src**：Docker 分层缓存。
改代码时 pom.xml 没变，依赖层缓存命中，不用重新下载依赖。

这些都是本项目开发过程中**真实遇到并解决**的问题。

## 环境类

### 坑 1：`characterEncoding=utf8mb4` 报错

```
Unsupported character encoding 'utf8mb4'
```

**原因**：JDBC 的 `characterEncoding` 要的是 **Java 字符集名**（`UTF-8`），
不是 MySQL 的字符集名（`utf8mb4`）。

**正确写法**：`characterEncoding=UTF-8`

### 坑 2：`spring.config.import` 的优先级陷阱

**现象**：`application-dev.yml` 里写 `password: ${DB_PASSWORD:}`，
结果把 `application-local.yml` 里的真实密码**覆盖**成了空值。

**原因**：`spring.config.import` 导入的文件**优先级低于**导入它的文件。

**解决**：dev.yml 里**彻底不写** password 字段。

### 坑 3：Redis 在 Windows 上"启动后窗口无输出"

**原因**：`redis.conf` 里 `logfile` 指向了 Windows 路径，
Cygwin 版 Redis 处理不了。

**解决**：`logfile ""`（空字符串）。

### 坑 4：bat 脚本乱码 + 闪退

**原因**：文件是 GBK 编码，却写了 `chcp 65001`（要求控制台按 UTF-8 读）。
更严重的是 **cmd 会按字节偏移执行 bat**，切换代码页后字节错位，
解析器读到垃圾内容就中断了。

**解决**：**GBK 文件就别碰 chcp**（中文 Windows 默认代码页就是 936）。

### 坑 5：命令行 `java` 命令崩溃

**原因**：PATH 第一位是失效的 `C:\Program Files\Common Files\Oracle\Java\javapath`，
它指向的目录已被删除。

**表现**：Maven 正常（走 JAVA_HOME），但命令行的 `java` 报错。

**解决**：从 PATH 里移除这个失效条目。

### 坑 6：沙箱环境变量污染

**现象**：Spring Boot 启动报 `Port 49987 already in use`。

**原因**：IDE 注入了 `SERVER__PORT=49987`，被 Spring Boot 当成了 `server.port`。

**解决**：测试脚本里 `unset SERVER__PORT`，并显式传 `--server.port=8080`。

## 框架类

### 坑 7：Swagger 启动失败

**原因**：Spring Boot 2.6+ 默认用 `PathPatternParser`，而 Knife4j 依赖 `AntPathMatcher`。

**解决**：

```yaml
spring:
  mvc:
    pathmatch:
      matching-strategy: ant_path_matcher
```

### 坑 8：404 响应格式不统一

**现象**：接口 404 时返回的是 Spring 默认的错误页，不是我们的统一响应体。

**第一次尝试（失败）**：配 `throw-exception-if-no-handler-found: true` +
`add-mappings: false`。404 是统一了，但 **`/doc.html` 也 404 了**（静态资源被关掉）。

**最终方案**：保留静态资源映射，**自定义 `CustomErrorController` 接管 `/error`**。

### 坑 9：`ErrorController.getErrorPath()` 编译失败

**原因**：Spring Boot 2.5+ 已移除这个方法。

**解决**：删掉对它的实现。

### 坑 10：MyBatis 类型别名解析不到 VO

**现象**：启动报 `Could not resolve type alias 'CourseVO'`。

**原因**：`type-aliases-package` 只注册了 `entity` 包。

**解决**：

```yaml
type-aliases-package: com.nnuist.coursehub.entity,com.nnuist.coursehub.vo
```

> ⚠️ **这是本项目第二次踩这个坑**（M1 时 UserMapper 只用 entity 没暴露问题，
> M2 课程模块用了 VO 就炸了）。

### 坑 11：`Collection` 实体与 `java.util.Collection` 别名冲突

```
The alias 'Collection' is already mapped to the value 'java.util.Collection'
```

**原因**：MyBatis 内置别名里已经有 `Collection`。

**解决**：给实体加注解指定别名：

```java
@Alias("CollectionEntity")
public class Collection implements Serializable { ... }
```

## 业务类

### 坑 12：PUT 接口部分更新被拒

**现象**：只想改教师名，返回 `40001 课程名称不能为空`。

**原因**：PUT 是**全量更新**语义，而 `name` 有 `@NotBlank` 校验。

**解决**：前端编辑时提交**完整字段**。（这是 REST 语义的必然要求）

### 坑 13：种子数据一直没导入

**现象**：登录一直失败，查不出原因（因为"账号不存在"和"密码错"返回同一个码，
这是**故意的安全设计**）。

**原因**：`init_data.sql` 写好了但**从没执行过**。

**教训**：脚本写完后要**确认真的执行了**。

### 坑 14：npm install 不完整

**现象**：`vite build` 报 `Rollup failed to resolve import "@floating-ui/dom"`。

**原因**：第一次 `npm install` 没装全，且没生成 `package-lock.json`。

**解决**：重跑 `npm install`。

**教训**：**`package-lock.json` 是否生成，是安装完整性的标志**。

## 测试类

### 坑 15：中文参数未 URL 编码

**现象**：搜索测试失败，接口收不到关键词。

**解决**：`urllib.parse.quote('数据结构')`

### 坑 16：测试数据没清理导致断言失败

**现象**：第二次跑测试，"首次上传不是秒传"断言失败。

**原因**：上次的数据还在，MD5 已存在 → 秒传命中。

**解决**：`verify-*.sh` 脚本里加清库语句。

### 坑 17：后台任务结束后子进程被回收

**现象**：测试脚本报"后端未就绪"，但日志显示后端启动成功了。

**原因**：用 `bash verify.sh &` 再在外层 `sleep`，
脚本内启动的 Java 进程在命令结束时被回收。

**解决**：**把"启动 → 等待 → 测试 → 清理"放在同一条命令内前台执行**。

> ⚠️ **这是本项目最耗时的坑**，试了 4 次才定位。

### 坑 18：测试脚本解包写错

**现象**：`ValueError: too many values to unpack (expected 2, got 5)`

**原因**：`upload()` 返回一个 dict（有 5 个键），
却写成 `c, b = upload(...)` 想解包成两个值。

**解决**：改成 `b = upload(...)`。

## 从这 18 个坑里能总结什么

| 类别 | 教训 |
|---|---|
| **环境** | 配置问题往往表现为"奇怪的现象"，要用**排除法**逐项验证 |
| **框架** | 框架版本升级会带来**不兼容**，看官方 Release Notes 比搜索快 |
| **业务** | REST 语义（PUT 全量/PATCH 部分）要在设计时就明确 |
| **测试** | **测试数据必须隔离**，否则第二次跑就失败 |
| **工具** | 报错信息里的**关键词**直接搜，通常能找到答案 |

# 第 18 章 开发流程总结：一个功能的完整生命周期

假设现在要加一个新功能：**"资料点赞"**。完整流程是这样：

## 第 1 步：想清楚需求

```
· 谁能点赞？    → 登录用户
· 能重复点吗？  → 不能
· 要记什么？    → 谁点了哪条资料、什么时候
· 要显示什么？  → 点赞总数、我点过没有
```

## 第 2 步：设计数据库

```sql
CREATE TABLE resource_like (
    id          BIGINT UNSIGNED AUTO_INCREMENT,
    resource_id BIGINT UNSIGNED NOT NULL,
    user_id     BIGINT UNSIGNED NOT NULL,
    created_at  DATETIME DEFAULT CURRENT_TIMESTAMP,
    PRIMARY KEY (id),
    UNIQUE KEY uk_resource_user (resource_id, user_id)    -- 防重复
);

-- 给 resource 表加个冗余计数
ALTER TABLE resource ADD COLUMN like_count INT NOT NULL DEFAULT 0;
```

## 第 3 步：设计接口

| 方法 | 路径 | 作用 | 是否登录 |
|---|---|---|---|
| POST | `/api/resources/{id}/like` | 点赞 | ✅ |
| DELETE | `/api/resources/{id}/like` | 取消点赞 | ✅ |
| GET | `/api/resources/{id}/liked` | 我点过没 | ✅ |

## 第 4 步：写代码（从上往下 or 从下往上都行，但要**按层写**）

```
① entity/ResourceLike.java          ← 对应表
② mapper/ResourceLikeMapper.java    ← 接口
③ resources/mapper/ResourceLikeMapper.xml  ← SQL
④ service/LikeService.java          ← 业务接口
⑤ service/impl/LikeServiceImpl.java ← 业务实现（含防重复、计数维护）
⑥ controller/LikeController.java    ← 接口
```

**每一层的职责**：

| 层 | 只做 |
|---|---|
| Controller | 收参数、校验、调 Service、包装响应 |
| Service | 业务规则、事务、权限 |
| Mapper | 执行 SQL |

## 最后：这个项目教会了我们什么

| 层面 | 收获 |
|---|---|
| **架构** | 分层不是为了好看，是为了"改一处不影响别处" |
| **安全** | 每一个用户输入都是不可信的，都要校验 |
| **性能** | N+1 查询、索引、缓存、Offline 计算 —— 都是同一个思路：**别做重复的事** |
| **数据** | 冗余字段换性能、逻辑删除换可恢复、版本表换可追溯 |
| **工程** | 测试、文档、提交规范 —— 让项目能被别人（和半年后的自己）接手 |

> **最重要的一条**：
> 所有的"最佳实践"都是**在具体场景下权衡的结果**，不是教条。
> 知道"为什么这么做"和"不这么做会怎样"，比记住"该怎么做"重要得多。
